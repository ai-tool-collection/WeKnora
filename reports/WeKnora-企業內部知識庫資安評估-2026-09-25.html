結論與導入判斷

不建議直接複製範例設定、拉取 latest 映像後接入正式內部文件。 本次靜態檢視未找到「在未設定外部服務時，主服務偷偷把所有知識庫資料固定傳回騰訊」的直接證據；但這不能證明沒有外洩，也不涵蓋預建映像的實際位元組、執行時網路行為或未啟用的程式路徑。已確認數個可造成資料離開公司邊界的設計與不安全預設值，必須先處理。

可以自行修改、在公司內部部署。專案主體授權為 MIT，允許修改與內部使用；第三方元件仍須遵守各自授權。可行的導入路徑是：固定且審核原始碼版本、自行建置並保存映像雜湊、限制所有容器及用戶端出站、僅使用受公司控制的模型與儲存、關閉外部追蹤與高風險代理功能、完成紅隊式外洩驗收後再放入敏感資料。

逐項分析與修正

F01 極高缺少有效 AES 主金鑰時，多種憑證可明文落庫

已確認的程式行為｜直接影響資料庫與備份保密性

.env.example 將 SYSTEM_AES_KEY 留空；GetAESKey() 在未設定或非 32 bytes 時回傳 nil。ModelParameters.Value()、資料來源、API Key 等欄位採「有金鑰才加密」：沒有金鑰時仍繼續儲存原值。這是可自行修正的失效開放行為；即便 DB 只在內網，備份、快照、管理員查詢及 DB 權限遭竊都會看到原始憑證。

修正：部署前透過祕密管理器提供高熵 32-byte SYSTEM_AES_KEY，所有副本使用相同值；程式啟動時在正式模式沒有正確長度就失敗；所有寫入敏感欄位的路徑在無金鑰時拒絕儲存。對已上線且未設金鑰的環境，先隔離 DB／備份，盤點明文欄位並輪替外部金鑰，最後加密重寫資料。

證據：.env.example:548-558、internal/utils/crypto.go:17-39、internal/types/model.go:253-269、internal/types/datasource.go:531-548、internal/types/tenant_api_key.go:245-258。

F02 高預設日誌會留下敏感查詢與部分對話內容

已確認的程式行為｜日誌通常複製到集中平台並長期保留

Compose 把主 app 的 LOG_LEVEL 預設設為 debug；程式在 info 級別記錄知識問答查詢、代理查詢與序列化 session，在 debug 級別記錄訊息內容預覽。即使只改成 info，完整 query 仍會被記錄；若外部日誌服務、客服或委外維運可讀取日誌，保密資料就已跨出原來的權限邊界。

修正：正式環境至少設 LOG_LEVEL=warn、LLM_DEBUG_LOG=false；更根本的修補是刪除或遮罩 query、session JSON、prompt、SQL 與模型回覆的日誌內容，僅留 request ID、長度、耗時及錯誤代碼。檢查日誌收集器、保留期限、權限及舊日誌清除。

證據：docker-compose.yml:80-90、internal/logger/logger.go:322-341、internal/application/service/session_knowledge_qa.go:694-698、internal/application/service/session_agent_qa.go:47-49、internal/agent/think.go:529。

F03 高雲端文件解析會送出整份原始文件

選配｜設定解析器及憑證後才會發生

WeKnoraCloud 的 reader 把 FileContent 轉成 base64，POST 到 https://weknora.weixin.qq.com/api/v1/doc/reader；MinerU Cloud 取得上傳 URL 後 PUT 原始文件；PaddleOCR-VL Cloud 使用 multipart file 上傳。SSRF 驗證只檢查目的位址是否安全，並不阻止上傳機密文件。這些功能對公司內部文件應視為完整資料揭露給該雲端服務。

修正：只提供本地 docreader／內部 OCR，從 UI、API 與模型 catalog 移除不允許的雲端解析器；防火牆封鎖上述端點，並用合成 canary 文件驗證無請求。若業務必須使用，先完成供應商、地區、保留期限與資料處理合約審查。

證據：internal/infrastructure/docparser/weknoracloud_http_reader.go:23,73-97、internal/infrastructure/docparser/mineru_cloud_converter.go:118-174、internal/infrastructure/docparser/paddleocr_vl_cloud_converter.go:130-150。

F04 高遠端模型服務會收到問題、知識片段及衍生內容

選配｜建立並選用外部模型時發生；非所有模型都指向騰訊

專案內建眾多模型供應商，包括騰訊混元、騰訊 LKEAP、OpenAI、其他中國與國際服務。RAG 問答會把使用者問題與取回的知識片段組裝為提示詞；embedding、rerank、VLM、ASR、摘要與圖譜抽取也可能傳送片段、圖片或音訊。供應商名稱只代表可選端點，程式碼中有端點常數並不代表預設已向該供應商送資料。

修正：採內部 Ollama／vLLM 或公司核准的私有模型端點；同時將 chat、embedding、rerank、VLM、ASR、文件後處理及 wiki 生成逐一指定為內部服務。把模型設定變更權限定給少數管理員，禁用任意 base_url 或透過網路 egress allowlist 約束。

證據：internal/models/providers/hunyuan.go:71、internal/models/providers/lkeap.go:58-61、internal/models/utils/ollama/ollama.go:32、config/config.yaml:11-50、README.md:312-323。

F05 高Langfuse 一旦有兩把金鑰，便可能傳輸完整提示詞與回覆

選配，但開關具有自動啟用特性

LANGFUSE_PUBLIC_KEY 與 LANGFUSE_SECRET_KEY 同時非空時，且未明確設 LANGFUSE_ENABLED=false，追蹤會自動啟用。預設主機是 https://cloud.langfuse.com；範例檔雖把主機設為內部 langfuse-web，卻也填了非空佔位金鑰，直接複製會嘗試啟用追蹤。chat wrapper 記錄 prompt、response 和 token；embedding 亦記錄輸入全文或預覽。HTTP trace 還含原始 query string。

修正：明確設 LANGFUSE_ENABLED=false，清空兩把金鑰；若須追蹤，僅用自建內網主機並設內容遮罩、縮短保留期限。程式可改為要求明確 true 才啟用，且拒絕在正式環境使用公網 Langfuse 主機。

證據：internal/tracing/langfuse/config.go:63-83、internal/tracing/langfuse/exporter.go:18-42、internal/models/chat/langfuse_wrapper.go:13-47、internal/models/embedding/langfuse_wrapper.go:18-70、internal/tracing/langfuse/middleware.go:43-55、.env.example:676-697。

F06 高瀏覽器呈現內容時可主動連到第三方

一般前端路徑｜使用者看到網頁引用或遠端圖片時

引用抽屜把網站網域拼成 https://www.google.com/s2/favicons?domain=…，再作為 <img src> 載入。這至少向 Google 揭露員工 IP、來源頁與所引用的網域；若內部網址被列為網頁引用，內網網域也可能被送出。Markdown sanitizer 允許 HTTP(S) 圖片來源，因此不可信文件、工具結果或模型輸出中的圖片 URL 也可令員工瀏覽器連向外部追蹤端點。這與伺服器的 SSRF 防護是不同邊界。

修正：移除 Google favicon 請求，改本地圖示或公司代理快取；將一般 Markdown 的遠端圖片改成點擊後載入或後端同源代理，並在正式前端設定嚴格 img-src 'self' blob: data: 與 connect-src。需先盤點合法物件儲存與嵌入頁需求。

證據：frontend/src/utils/referenceSources.ts:82-89,151-165、frontend/src/components/ChatReferencesDrawer.vue:127-134、frontend/src/utils/markdownDomPurify.ts:4-18,72-91、frontend/src/utils/security.ts:326-348。

F07 高代理、技能與沙箱形成可程式化資料出口

條件式｜預設 Docker 沙箱關閉；啟用沙箱／工具後需額外治理

代理可使用網頁搜尋、抓頁、MCP、瀏覽器和可安裝技能。技能可從 ClawHub／SkillHub／GitHub 取得；安裝驗證只確認格式與部分語法，不能保證腳本安全。沙箱儲存的網路政策為空時預設允許出站；Docker 沙箱在允許時用 bridge，只有 none 可保證無網路。帶有惡意指令的文件或網頁可能誘使代理把可讀資料送至外部工具。Docker socket 若掛到 app，等同把宿主機高權限交給該服務。

修正：首階段關閉 Docker／E2B／Cube 沙箱、外部技能商店與不必要的 MCP、瀏覽器、網路搜尋；有業務需要時，每個工具個別審批，沙箱設拒絕出站為預設並隔離其檔案與公司網段。不要將主機 Docker socket 掛到處理機密資料的 app。

證據：docker-compose.yml:47-55,101,394-405、internal/sandbox/tenant_config.go:305-324、internal/sandbox/docker_remote_client.go:357-373、internal/application/service/tenant_skill_source.go:26,92-123、internal/agent/tools/web_search.go:95-176。

F08 高Compose 預設暴露 HTTP，且允許自助註冊

部署條件｜在公司內網也須視其他租戶與橫向移動風險

前端 80:80、API 8080:8080 未指定 host IP，Docker 會預設綁所有介面；範例用 HTTP，DISABLE_REGISTRATION=false，資料庫與 Redis 範例密碼也是固定示範值。API 有 JWT、API Key、RBAC 及公開路由，但部署者若把主機開到廣泛網段，可能讓任何能連到服務的人註冊與使用空間。資料庫及 Redis 在標準 Compose 中未直接 publish，風險重點是憑證弱、同一 Docker 網路與主機被入侵後的橫向存取。

修正：以公司 SSO／OIDC、邀請制和反向代理 TLS 管控入口；API 只綁 loopback 或內網 ACL，對員工僅暴露 TLS 前端，禁止自助註冊及普通使用者自建空間；更換所有示範密碼並管控初始化管理員。

證據：docker-compose.yml:15-16,45-46,125,531-565、.env.example:136,151,548-572、internal/config/config.go:835-860、internal/middleware/auth.go:29-57。Docker 未指定 host_ip 的行為見文末官方文件。

F09 高原始碼審核無法覆蓋未固定映像與桌面更新

供應鏈風險｜目前未驗證任何預建映像

Compose 的主要 WeKnora 映像標籤預設 latest；Dockerfile.app 的建置流程還使用 migrate@latest、遠端安裝腳本與第三方建置素材。部分前端基底映像已固定 digest，這是正向作法，但整體仍未做到可重現建置。桌面版前端預設自動檢查更新，Go 程式讀 GitHub release、背景下載資產；本次在更新路徑未找到下載後 SHA-256／簽章驗證，安裝需使用者選「Restart Now」，並非無互動立即執行。桌面版若導入公司內部，此路徑是另一個供應鏈入口。

修正：以審核 commit 自建所有映像，鎖定 digest 並留存 SBOM、簽章及雜湊；固定所有建置工具與下載來源，避免 curl | sh。內部桌面版關閉自動下載，改走公司更新服務及簽章驗證。

證據：docker-compose.yml:3,37,408、docker/Dockerfile.app:9,39,119-121、frontend/Dockerfile:26,59、frontend/src/stores/settings.ts:111、frontend/src/App.vue:244-265、cmd/desktop/update.go:53-67,103-121,214-289,315-410。

F10 中應用層 SSRF 檢查不是完整資料防火牆

部分防護已存在｜仍需以網路層限制對外連線

專案提供 ValidateURLForSSRF、安全 HTTP client、重新導向與 DNS 防護；docreader 也有對應防護。SSRF_DNS_WHITELIST_ONLY 預設關閉，啟用時白名單成為目的地主機政策，但它不能自然涵蓋所有 SDK、模型用戶端、瀏覽器資源或沙箱。即便請求目的地是「安全的公網 IP」，把文件內容 POST 到那裡仍是外洩。

修正：對主 app、docreader、沙箱與員工瀏覽器分別設 deny-by-default egress；白名單只放內部模型、DB、必要解析器與受控代理。用防火牆／Kubernetes NetworkPolicy／企業代理做實際拒絕，再用程式白名單作第二層。

證據：internal/utils/security.go:794-821,1176-1222,1294-1340、docreader/utils/ssrf.py:130-138,270、docker-compose.yml:306-322,432-434、.env.example:757-773。

F11 中整合可把內部內容送往公司之外

選配｜MCP、IM、外部資料來源、搜尋、向量／物件儲存

搜尋 provider 會收到查詢；IM 渠道可能傳出回覆與檔案連結；MCP server 或任意工具可能收到參數、工具結果與授權資訊；第三方物件或向量儲存可收到文件和向量。這些並非「騰訊後門」，而是可由管理員選用的資料出口。獨立 MCP 容器在 full profile 下才啟動，且程式註解指出 HTTP/SSE 缺 MCP_SERVER_AUTH_TOKEN 應拒絕啟動；仍需驗證實際設定及管理權限。

修正：以清單核准每個整合服務、可送的資料等級和網域；預設不建任何外部 provider，限制誰可修改模型、工具、web search、MCP、資料來源與儲存設定。需審核第三方保留與訓練政策。

證據：README.md:312-325、internal/router/routes_infra.go:152-193,211-244、internal/agent/tools/web_search.go:134-176、docker-compose.yml:1008-1034。

F12 中短效資源連結仍是持有即存取的能力

選配｜嵌入頁、IM 圖片、外部可達檔案／物件儲存

部分客戶端無法帶登入 Header，因此系統提供簽章或短效的資源 URL。這類設計有有效期限與簽章檢查，但連結若進入外部 IM、日誌、瀏覽器歷史、轉址或第三方頁面，在有效期內取得者可能讀取資源。若將 MinIO／COS 或 APP_EXTERNAL_URL 設為公網可達，風險會擴大。

修正：內部知識庫優先使用需登入的同源下載；確實需 IM／嵌入時縮短 TTL、限制路徑／租戶／用途，避免在日誌記錄完整 URL，審核引用者與外部可達性。

證據：internal/utils/presign.go:26-64,109-185、internal/router/router.go:193-219、docker-compose.yml:107-111。

F13 中docreader 預設只靠網段隔離保護文件傳輸

標準 Compose 只在內部網路 expose，跨主機部署時風險增加

文件解析 gRPC 預設 GRPC_TLS_ENABLED=false、GRPC_AUTH_TOKEN 空白；標準 Compose 沒有 publish 50051，這降低外部暴露。若為擴容把 docreader 服務開到共享網段，原始文件就可能在未加密、未認證的連線上傳輸或被同網段服務呼叫。

修正：保持只在受控內部網路可達；跨主機時啟用 TLS／mTLS 與至少 16-byte 隨機 token，限制 app 到 docreader 的來源 IP，檢驗憑證與 token 的部署一致性。

證據：docker-compose.yml:407-446、.env.example:405-409、.env.lite.example:91-95。

已具備的防護，以及它們的邊界

  • 存取控制：後端有 JWT／API Key、租戶脈絡、RBAC 與多數路由的角色檢查；公開的登入、註冊、短鏈與嵌入路由也在程式中明列。這不取代 SSO、入口網路 ACL 和實際權限測試。參考 internal/router/router.go:208-257、internal/router/rbac.go、internal/middleware/auth.go:29-57。
  • SSRF：多處 URL 呼叫使用安全 HTTP client，部分支援僅白名單出站；它解決內部位址探測的一部分問題，不能判斷文件內容能否送給公網供應商。參考 internal/utils/security.go:794-821。
  • 前端 XSS：Markdown 與 HTML 經 DOMPurify 清理、禁用腳本及事件屬性；但合法 HTTP(S) 圖片仍可造成被動網路請求。參考 frontend/src/utils/markdownDomPurify.ts:1-18,72-91。
  • 部署隔離：標準 Compose 未 publish PostgreSQL、Redis 和 docreader；Docker 沙箱預設關閉。請勿因而忽略公開的 80／8080、同網路橫向存取、出站通道與備份權限。參考 docker-compose.yml:15-16,45-46,394-445,531-565。
  • 加密能力：有 AES-256-GCM 與帶簽章資源連結；部署者必須提供有效且可持續保管的金鑰，否則部分欄位會明文儲存。參考 internal/utils/crypto.go:17-58、internal/utils/presign.go:26-64。

其他交付面與部署差異

  • Helm 與 Compose 的金鑰行為不同。F01 的「範例金鑰留空而明文落庫」主要適用於直接執行／複製 Compose 範例卻不填 SYSTEM_AES_KEY 的情況。Helm chart 在沒有指定金鑰時會產生 32 字元隨機值，並於升級時嘗試重用既有 Secret；若 Secret／叢集遺失，舊資料仍可能無法解密。Helm 會要求 DB、Redis、JWT 密碼，卻沒有在此 chart 找到 NetworkPolicy 範本，網路出口仍需公司自行設。證據：helm/templates/secrets.yaml:16-50、helm/values.yaml:401-422。
  • Helm 仍有浮動映像。app tag 預設跟隨 Chart.appVersion，但 UI、docreader、MinIO 與 Qdrant 在 values 內使用 latest。不論採 Compose 或 Helm，都應對每個映像採 digest 固定。證據：helm/Chart.yaml:8、helm/values.yaml:65-71,159-165,206-212,431-433,496-498。
  • 微信小程式是獨立用戶端。其程式把 API Key 保存在 wx.setStorageSync，並將它放入每次請求的 X-API-Key；使用者可設定 API base URL，程式僅 trim URL，沒有自行要求 HTTPS。若公司不打算使用小程式，無需部署；若使用，請發最小權限、可撤銷的專用金鑰，固定受管 HTTPS 端點並審查裝置／平台政策。證據：miniprogram/utils/config.js:1-39、miniprogram/utils/request.js:4-23、miniprogram/app.js:1-13。
  • CLI 與 dsh 套件。本次在 CLI 的重點搜尋未發現獨立固定遙測端點；它及 Go client 主要依使用者設定的 WeKnora host 呼叫 API。packages/dsh-weknora 的資源 URL 模式預設為 public，程式會在請求中加入 resource_urls=public；權限不足時改用 handle。公司若接入外部代理平台，應明確改為 handle，並檢查該平台是否保存檢索片段與連結。證據：client/client.go:122-171、packages/dsh-weknora/src/config.ts:65,152-177、packages/dsh-weknora/src/client.ts:129-150。
  • 建置與雲映像初始化會產生其他連線。下載依賴、GitHub／BrowserSkill 原始碼、Rust／uv 安裝腳本及模型清單屬供應鏈／建置流量；scripts/cloud-image/firstboot.sh 還會查詢 ifconfig.me 或 api.ipify.org 以取得主機公網 IP。這段腳本的程式碼未顯示上傳知識庫內容，但隔離建置與正式資料、停用不必要初始化外連仍是合理作法。證據：docker/Dockerfile.app:9,39,119-121、scripts/build_browserskill.sh:35、scripts/cloud-image/firstboot.sh:104-105。

上線驗收與剩餘風險

應完成的可觀察驗收

  1. 用合成且唯一的 canary 字串各放入文件、文件名、圖片、問答與 API 金鑰欄位；走上傳、解析、檢索、代理、匯出、刪除流程。查防火牆與 DNS／HTTP 代理紀錄，確認只有批准端點，且目的地沒有 canary。
  2. 在空金鑰與錯誤長度金鑰下啟動服務，驗證正式模式拒絕啟動或拒絕寫入；用有效金鑰儲存後直接檢查 DB 欄位無明文。備份與還原測試需保證金鑰管理安全。
  3. 檢查容器與反向代理的實際監聽位址、TLS、匿名註冊、OIDC、租戶權限；用一般使用者嘗試建立外部模型／MCP／sandbox 並確認被拒。
  4. 使用含惡意指令與遠端圖片 URL 的測試文件；觀察代理工具、瀏覽器 DevTools Network 與 egress log，確認不能把內部片段送到未批准網域。
  5. 對自行建置映像比對 commit、依賴鎖定檔、SBOM、漏洞掃描與簽章；不要以本報告對原始碼的檢視代替映像審查。每次升級重做。
風險接受條件。上述 P0 修補完成、網路 deny-by-default 及 canary 測試通過後，可先用非機密文件試行。若要導入機密或個資，仍需依公司政策完成滲透測試、資料分類、第三方合約及持續監控。沒有執行期流量與實際映像證據前，無法宣稱「零資料外洩風險」。
